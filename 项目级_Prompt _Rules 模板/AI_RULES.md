# AI_RULES.md — Coding Agent 行为守则与工程红线规范

> **文档性质**：项目级行为准则文档（**最高强制执行级别**）。  
> **适用对象**：后续所有参与本项目代码编写、重构、调试、测试的 Coding Agent 及开发人员。  
> **核心宗旨**：保障嵌入式系统底层稳定性、绝对遵守考核评分红线、严格遵循分步研发工序、禁止越界与私自设计。

---

## Rule 0 — Strictly Follow the 15-Step Guided Development Pipeline (15步引导式开发流程铁律)

本项目严格遵循以下 15 步结构化嵌入式系统研发工序：

```text
                【自然语言需求】
                       │
                       ▼
                ① 需求分析 (系统到底需要做什么？)
                       │
                       ▼
                ② 需求量化 (什么条件、什么时间、什么结果？)
                       │
                       ▼
                ③ 硬件资源映射 (GPIO / UART / ADC / PWM / Timer)
                       │
                       ▼
                ④ 系统行为设计 (状态机 / 工作流程)
                       │
                       ▼
                ⑤ 软件架构设计 (BSP / Driver / Service / App)
                       │
                       ▼
                ⑥ 模块划分 (Motor / Sensor / Comm / Control)
                       │
                       ▼
                ⑦ 接口设计 (每个模块对外提供什么？)
                       │
                       ▼
                ⑧ 数据设计 (状态 / 参数 / 缓冲区 / Context)
                       │
                       ▼
                ⑨ 时序设计 (周期 / 中断 / 任务 / 超时 / 调度)
                       │
                       ▼
                ⑩ 异常与边界设计 (非法输入 / 超时 / 掉线 / 溢出)
                       │
                       ▼
                  【编码实现】
                       │
                       ▼
                ⑪ 模块测试
                       │
                       ▼
                ⑫ 功能联调
                       │
                       ▼
                ⑬ 系统测试
                       │
                       ▼
                ⑭ Code Review
                       │
                       ▼
                ⑮ 最终版本
```

### 核心执行原则：
1. **用户主导步调**：所有开发环节必须由用户明确引导发起。
2. **每次对话最多推进一个步骤**：一个步骤可能需要经过多轮对话沟通与迭代确认。**严禁在当前步骤未经用户审核确认前，私自跳跃执行后续步骤**！
3. **禁止提前编码与私自设计**：在完成 ①~⑩ 步系统设计之前，绝对不允许私自编写业务代码、私自固化数据结构或私自决定架构方案。

## Rule 1 — Inspect Before Editing (先调查，后修改)

1. 在修改或新增任何代码前，**必须先使用读取工具检查相关文件的现有实现**。
2. 严禁基于文件名、函数名猜测现有代码的入参、返回值或内部逻辑。
3. 若任务涉及跨模块交互，必须先沿完整调用链梳理数据流向与变量生命周期。

---

## Rule 2 — Respect Existing Architecture (尊重既有架构，禁止无关重构)

1. 必须严格遵循当前工程已经确立的硬件配置与分层结构。
2. **严禁为了实现单一小功能而进行全工程重构**（如擅自引入 FreeRTOS、替换 HAL 库底层结构等）。
3. 如确实发现现有设计存在不可调和的逻辑缺陷，必须先向用户指出原因与影响范围，获取用户明确许可后方可实施修改。

---

## Rule 3 — Do Not Invent APIs (禁止凭空捏造函数与变量)

1. 严禁假设项目中存在未曾声明的宏定义、全局变量、结构体成员或驱动函数。
2. 凡调用的 HAL 库接口，必须确认属于 STM32F1xx HAL 驱动库支持的合法 API。
3. 凡调用的用户层函数，必须先在头文件中找到对应原型声明。

---

## Rule 4 — CubeMX Safety (CubeMX 代码生成安全红线)

1. 必须精准识别并遵守 STM32CubeMX 代码生成机制。用户自定义代码**只能且必须**书写在：
   ```c
   /* USER CODE BEGIN xxx */
   // 你的代码在此处
   /* USER CODE END xxx */
   ```
2. 严禁在上述保护注释区间之外添加、修改代码，以防 CubeMX 再次生成时被无情覆盖。
3. 严禁擅自修改 `MX_xxx_Init()` 函数的函数签名与自动生成逻辑。

---

## Rule 5 — Embedded Constraints (时刻牢记嵌入式底层资源边界)

本项目运行于 **STM32F103C8T6**（Cortex-M3，72MHz，64KB Flash，20KB SRAM）：
1. **栈空间警戒**：两端工程栈空间配置为 `0x800` (2048 字节)。
   * **严禁在局部变量中开辟大型数组**！例如 1024 字节的 OLED 显存必须声明为静态全局变量（`static uint8_t`），绝对禁止放在栈上。
2. **硬件浮点缺失**：Cortex-M3 **无硬件 FPU**，单精度/双精度浮点运算均为软件库软解，开销巨大。在高频任务中，严禁进行无节制的复杂浮点运算或三角函数调用，优先考虑定点化或查表法。
3. **通信吞吐量意识**：串口波特率为 115200bps，理论每秒最大字符传输量为 11520 字节。通信协议设计与高频发送任务必须计算实际带宽，防止串口发送堵塞。

---

## Rule 6 — Avoid Unnecessary Dynamic Memory (严禁无节制动态内存分配)

1. **全面禁止在运行时使用堆动态内存分配**：严禁在循环或业务逻辑中调用 `malloc()`、`calloc()`、`realloc()` 和 `free()`。
2. 所有环形缓冲区、协议帧暂存区、显存缓冲区、状态机结构体必须采用**静态编译期分配**（`static` 或全局变量）。
3. 杜绝因内存碎片化导致的难以复现的 HardFault 异常。

---

## Rule 7 — Avoid Blocking Architecture (严禁阻塞式延时架构)

1. **严禁在主循环或高频任务中无节制调用 `HAL_Delay()`**！
2. 系统任务调度必须使用非阻塞的时间戳调度模型（基于 `HAL_GetTick()` 或硬件定时器比较）。
3. 状态跳转必须采用有限状态机（FSM），严禁通过长延时来等待硬件事件。

---

## Rule 8 — Interrupt Safety (中断服务程序极简与安全准则)

1. **中断服务程序 (ISR) 必须极致轻量**：
   * 仅允许执行：清除中断标志、搬移寄存器单字节至环形缓冲区、累加计数器、置位事件 Flag。
   * **绝对禁止在 ISR 中执行**：大型协议解析校验、复杂的姿态浮点运算、OLED 屏幕 I2C 刷新、任何阻塞等待、任何 `printf` 串口打印。
2. **中断与主循环共享数据安全**：
   * 所有在中断中修改并被主循环读取的全局变量/标志位，**必须显式添加 `volatile` 修饰符**。
   * 共享关键数据临界区时，必须评估是否需要短暂关闭中断以保证数据一致性（原子性读取）。

---

## Rule 9 — Buffer Safety (严格的缓冲区与数据越界防御)

所有数据传输与解析代码必须构建严格的越界防御：
1. 串口接收必须使用**带长度越界检查的环形缓冲区 (RingBuffer)**。
2. 协议解包器必须在读取数据载荷前验证 `Length` 字段的有效性。
3. 数组写入操作必须带有严格的边界断言或索引范围判断，坚决防止内存踩踏。

---

## Rule 10 — Protocol Compatibility (协议三端同步一致性法则)

1. 任何对通信帧协议（`PROTOCOL.md`）的字段增删、类型调整或字节序修改：
   * **手柄发送端 (Sender)**、
   * **接收解析端 (Receiver)**、
   * **PC 上位机协议解析 (如 VOFA+)**
   **必须三端保持原子级完全同步修改**！
2. 绝对不允许只修改单端代码而遗漏对端，导致现场调试时出现解析乱码或丢包率激增。

---

## Rule 11 — Error Handling (禁止吞并 HAL 状态返回值)

1. 针对 HAL 库硬件外设初始化、I2C 传输、SPI 传输和串口发送等关键 API，必须检查其返回值（`HAL_OK`, `HAL_ERROR`, `HAL_BUSY`, `HAL_TIMEOUT`）。
2. 严禁为了“代码简练”而忽略硬件通信超时处理。若 I2C/SPI 总线由于面包板信号干扰发生卡死，应具备超时重试或软件总线复位逻辑，防止单片机永远卡在死循环。

---

## Rule 12 — Keep main.c Small (保持 main.c 极简与高内聚)

1. `main.c` 只承担系统启动、时钟与外设初始化、中断使能及顶层协同调度分发的职责。
2. 具体的业务逻辑、算法实现、状态机跳转、显存绘制必须封装在对应的独立模块中，保持 `main.c` 清爽、易读且符合考核评审规范。

---

## Rule 13 — Preserve Scope (克制修改范围，禁止随意动迁)

1. 每次修改仅局限于完成当前指令所必须的最小文件集合。
2. 严禁在未获允许的情况下“顺便”更改不相干模块的变量命名、函数签名、排版格式，或删除看似暂时无用的代码。

---

## Rule 14 — Verification Checklist (代码产出必须完成 10 项自检)

每次完成代码编写或修改后，Agent 必须在内心逐项核对以下 10 项自检指标：
1. **编译层面一致性**：头文件包含是否完整，无未定义标识符。
2. **函数声明与定义**：参数类型、入参个数、返回值在 `.h` 与 `.c` 中是否 100% 吻合。
3. **类型位宽与字节序**：结构体对齐、`int16_t` / `uint16_t` 大小端是否一致。
4. **缓冲区边界检查**：是否具备索引上限拦截，无下溢或上溢风险。
5. **空指针与非法传参防护**：驱动函数是否判断了入参指针合法性。
6. **状态机闭环**：每个 `switch-case` 是否都有 `default` 分支及明确的重置条件。
7. **中断共享变量**：是否已全部标记 `volatile`。
8. **时钟与时间单位**：SysTick 时间戳计算（毫秒/微秒）单位是否统一。
9. **协议三端兼容**：协议改动是否已两端同步。
10. **硬件引脚与资源冲突**：引脚与定时器/通道配置是否与 CubeMX 事实完全一致。

---

## Rule 15 — Hardware Cannot Be Assumed (硬件行为绝不凭空猜测)

1. 遇到外设寄存器地址、I2C 从机地址（如 OLED 0x78）、SPI 时序模式（CPOL/CPHA）、IMU 内部量程寄存器等硬件细节时：
   * 优先查阅官方芯片 Datasheet、参考手册 RM0008 或 HAL 库头文件。
   * 严禁凭空编造芯片寄存器偏移量或从机应答逻辑。

---

## Rule 16 — Explain Changes (结构化汇报工作成果)

完成任何代码修改后，向用户汇报必须结构化说明：
* **修改的文件列表**（给出明确路径）；
* **修改原因与设计决策**；
* **数据流与状态机变动**；
* **推荐的验证步骤与自测方法**；
* **潜在风险提示与已知边界条件**。
